# Operation state, saved scenes, and recovery

The durable record is the project directory plus saved Blender files. Chat
summaries are navigation aids. A successful script call is not evidence of
historical accuracy or visual quality.

## Files and responsibilities

| File | Responsibility |
|---|---|
| `AGENTS.md` | Stable project rules. Read on initial launch and after compaction. |
| `progress/PROJECT_STATE.json` | Current stage, active operation, completed/failed operations and last committed checkpoint. Generated by the helper. |
| `progress/OPERATIONS.jsonl` | Append-only transition log. The state JSON is authoritative if a crash occurs before a log append. |
| `progress/checkpoints/<operation-id>/manifest.json` | Output hashes, checks recorded and scene association. |
| `progress/checkpoints/<operation-id>/state.json` | State candidate associated with this checkpoint. |
| `progress/checkpoints/<operation-id>/scene.blend` | Byte copy of the saved scene for that checkpoint, when `--scene` was supplied. |
| `NEXT_STEPS.md` | Short human-readable continuation instructions, blockers, exact next action and relevant briefs. Update after each meaningful batch. |
| `DECISIONS.md` | Stable decisions and historical approximation choices. |

Keep binary `.blend` files out of chat. Inspect through Blender MCP and store
compact inventories. Do not paste entire image/PDF payloads or tool logs into
`NEXT_STEPS.md`.

## State schema version 1

`schema_version` is `1`. `current_stage` is a stable short ID. `active_operation`
is `null` or the key of one pending operation. `last_checkpoint` and `scene_file`
are project-relative paths or `null`. `operations` maps unique operation IDs to:

- `id`, `stage`, `description`, `started_at`.
- `status`: `pending`, `complete`, or `failed`.
- `expected_outputs`: nonempty list of project-relative paths.
- `before_sha256`: hash before the operation, or `null` for a new output.
- Completed operations additionally contain `completed_at`, `verification`, and
  `checkpoint`. Failed operations contain `failed_at` and `failure`.

Operation IDs are never reused, including after failure. Use `river-01`, then
`river-02` for a corrected attempt. Paths accept forward slashes or Windows
relative backslashes. Absolute paths, UNC paths, parent traversal and symlinks
escaping the project are rejected by the state helper.

## Normal operation

Run external Python from the extracted kit's root. On Windows, substitute
`py -3` if that is how Python is installed. The helper uses only the standard
library and requires Python 3.10 or newer.

```powershell
python scripts/palagan_state.py init
python scripts/palagan_state.py status
python scripts/palagan_state.py reconcile
```

Before a scene mutation, record the precise task and outputs:

```powershell
python scripts/palagan_state.py begin --id blockout-01 --stage blockout --description "Build the approved river and street blockout" --expect output/blockout-01.blend --expect output/blockout-01.inventory.json
```

Perform that bounded operation in Blender through the MCP server's discovered
code tool. Save the scene and inventory using `scripts/blender_session.py`:

```python
import runpy, json
ROOT = r"C:\Projects\PALAGAN_Surabaya_Reconstruction_Kit"  # actual extracted path
api = runpy.run_path(ROOT + "/scripts/blender_session.py")
print(json.dumps(api["save_snapshot"](
    ROOT, "output/blockout-01.blend", "blockout-01"
), indent=2))
```

The `ROOT` example is a placeholder. Detect the actual path in OpenCode and use
it explicitly. The Blender helper imports `bpy`, so run it inside Blender,
not with external Python. It does not build the geometry itself.

Inspect the saved scene, required reference views and inventory. Then record
only checks that were actually performed:

```powershell
python scripts/palagan_state.py complete --id blockout-01 --scene output/blockout-01.blend --verification "Opened saved scene; checked overview and river crossing views against the approved layout; inventory contains the expected owned assets. Remaining approximations are recorded in DECISIONS.md."
```

Do not copy the example verification text if those checks were not performed.
Completion requires nonempty expected files and at least one changed/new
output. A deliberate no-change verification can use `--allow-unchanged`, but
its justification must be stated. For scene operations, always supply `--scene`.
This creates an independent `.blend` copy, which uses additional disk space.
Keep recent known-good checkpoints and do not prune them during an unfinished
operation.

The helper verifies saved bytes and state transitions. It does not open a
`.blend`, establish that Blender can reopen it, or prove that its contents match
a source. Those checks remain explicit Blender/visual review tasks.

## Resume after compaction, restart, or interruption

1. Read `AGENTS.md`, `NEXT_STEPS.md`, `DECISIONS.md` and
   `progress/PROJECT_STATE.json` if present.
2. Run `python scripts/palagan_state.py reconcile`. Exit `0` means no recorded
   checkpoint/pending-work issue was found. Exit `2` means inspection is required.
3. Through Blender MCP, inspect `bpy.data.filepath`, active scene, project-owned
   collection, asset IDs and `palagan_last_operation`. An unsaved live scene
   may be ahead of the last committed file.
4. If there is pending work, inspect it before rerunning. Do not assume it failed
   simply because the previous context disappeared. Existing geometry must be
   recognised using stable asset IDs.
5. If pending work is complete and its saved outputs pass the prescribed checks,
   complete that operation. If partial or wrong, preserve the scene, record
   `fail --id ... --reason ...`, then begin a new attempt ID.
6. Load only the briefs and source crops needed for the next bounded operation.

`reconcile` is read-only: it never loads a `.blend`, resets a scene, rewrites
history or silently changes pending work into complete work.

## Interrupted checkpoint commit

Checkpoint candidates are written before the live state is committed. A crash
can leave `progress/checkpoints/<id>/` while the operation remains pending.
The helper reports this as an orphan candidate and refuses to overwrite it.
Inspect its manifest, saved scene and state candidate. Preserve it under an
archive name outside `progress/checkpoints/` if it is incomplete, fail the
pending operation, then use a new ID. Do not hand-edit live state to mark it
complete. A saved file with no trustworthy operation record requires review.

A stale `.state.lock` is also possible after process termination. Confirm that
no `palagan_state.py` process is running before removing that one lock file.
The helper never automatically deletes a lock owned by an unknown process.

## Checkpoint discrepancies

Working output hashes may legitimately change during later pending work.
That is a signal to inspect, not proof of corruption. The independent checkpoint
scene should remain unchanged. If a checkpoint snapshot is missing or its hash
differs, do not use it as a known-good recovery file.

Atomic replacement protects individual JSON writes. It is not a database
transaction across multiple files and is not a guarantee against power loss,
disk failure, concurrent manual edits or deliberate modification. Keep a copy
of completed deliverables outside this working directory.

## Context hygiene

Checkpoint at meaningful boundaries: approved layout, river/streets, each
landmark, background block batch, materials and presentation. Update continuation
notes after each batch and before a costly operation. Do not wait for a token
count. The agent cannot reliably infer OpenCode's exact compaction threshold.

Keep `AGENTS.md` concise. Load asset briefs on demand. Store full logs on disk,
but return short summaries from tool calls. Auto-compaction does not preserve
an unsaved Blender scene and cannot recover facts never written down.

## Optional compaction plugin

`runtime/palagan-compaction.mjs` implements the documented
`experimental.session.compacting` hook and adds a bounded state excerpt to
`output.context`. It does not replace OpenCode's default summary, perform a
checkpoint, make model calls or force a session to resume.

First record `opencode --version`. Consult that version's official plugin
documentation. If the contract matches, copy this one file into the project's
`.opencode/plugins/` directory and restart OpenCode. If loading fails, remove
the copied file and continue using the file-based recovery protocol. Do not
change global OpenCode settings or assume V2 settings work in V1.
